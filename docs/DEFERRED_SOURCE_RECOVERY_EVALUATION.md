# 工具消息协议、候选与错误恢复优化

2026-09-20。最终代码对应 `native-protocol-recovery-20260920-b` 的源码快照。未修改引擎或重启 GPU 服务，未清空或修改用户日常码表。此前未提交的改动继续保留。

## 改动及边界

1. **恢复标准工具消息协议。** 过去把 assistant 的 toolCall 序列化为普通文本、把 toolResult 转成 user 消息。现在保留 `assistant.tool_calls`、`function.name/arguments`、`tool_call_id` 和 `role=tool`，错误状态及实际工具返回内容仍在工具结果中。计划结果中的顶层 `learning` 入表元数据只保留在原始日志/状态中，不再作为模型的任务验证反馈；嵌套的真实文件内容不受影响。远端 /tokenize 已接受此结构；历史消息不再把执行结果伪装成新的用户要求。
2. **候选保留全文，突出需求变化。** 分类前保留完整历史任务和完整源码，避免依靠不完整预览判断复用。对文本相近的历史任务，额外展示有上下文的词级差异，最多约 1000 字符并标记省略；相似度仅决定是否展示差异，不决定命中、不屏蔽候选。完整当前需求始终优先。候选仍最多七个，磁盘码表容量没有缩小；没有通过关键词规则替代 LLM 语义选择。

   **工具参数 schema 延后展示。** 分类阶段保留工具名称和描述，参数 schema 在选中后的 continuation 中完整提供，避免在 system 消息与生成 schema 中重复携带。所有分支仍支持原有参数校验及原生工具，不丢弃参数约束。
3. **恢复时保留失败证据。** 最新执行失败时展开工具参数和原始错误，避免多层 JSON 字符串转义；最新成功时不再把历史错误标成“最近执行失败”。完整过去错误仍保留于标准工具消息历史。只有缺陷仍未解决才提示执行修复，成功验证后允许正常结束；读取成功本身不作为任务已完成的证明。
4. **恢复动作带简短目的。** 仅错误恢复模式要求每个步骤先生成 `purpose`（最多 240 字符），描述本次动作针对的缺陷，然后生成原生工具及参数。此字段在解码时校验并移除，不会传给 Pi 原生工具；日志记录目的。沿用一次引擎请求及 plan 包装，不新增 verifier 模型请求，不改变每子工具参数 2048 的限制。目的文字也计入生成 token，因此可能增加单次生成成本。
5. **测试隧道可靠性。** SSH 增加保活、stderr 归档及每个任务前的进程检查。断线后停止测试，不让后续全部任务继续请求失效端口。测试器不自动重试或恢复，网络失败仍保留。

此前的重复失败保护继续保留；它只识别连续参数完全相同的失败计划，不能阻止改变命令写法的循环。码表入表仍只证明执行成功，不证明符合所有需求。本轮未新增通用语义验证器。

## 实验过程与保留的失败

- **a 轮**：完全隐藏分类前的源码，并直接把完整 diff 放入目录。输入因重复旧合同反而变大，多项重复任务不复用。JSONL changed 产物错误；intervals changed 被重复失败保护中止。随后测试用 SSH 子进程退出，两组均出现 HTTP 503，配置任务虽已产出正确文件但未正常结束。只读检查确认远端服务 /health 为 200、容器仍运行且无任务，重建测试隧道后恢复真实推理。人工停止时记录了 31/42 次尝试，另有未完成日志；这是不完整试验，不能报成 21 题完整成绩。
- **b 轮**：限制合同预览长度、目录仅展示 diff 新增行，并改正分类提示要求读取尚未展示源码的矛盾；仍隐藏源码。朴素 21/21、203.968 秒；TAIR 19/21、275.055 秒，复用零次。TAIR 两项重复失败后停止；仅已记录生成 token 14022、输入 446145，用量完整标记为 false。42 份保存产物重新验收与原 oracle 一致。没有将此版作为码表优化成功结果。
- **恢复 purpose 冒烟测试**：新 schema 在真实服务可执行，TAIR 修复任务正常完成，确有 purpose 生成和工具恢复。朴素此次未触发初始失败，因此不能拿它证明相同失败恢复成本。
- **c 轮**：恢复有限源码预览、保留失败证据并加入 purpose。朴素 21/21、227.757 秒；TAIR 18/21、244.187 秒，复用一次。三个失败均为未执行就回复：JSONL repeat、SQL changed、chunks changed。JSONL changed 和区间 changed 确实完成错误恢复，后者两次错误后重跑检查成功，但总体质量仍不合格。42 份保存产物复验一致；源码隐藏与截断方案均回退，不因生成 token 减少就保留。
- **d 轮**：恢复完整候选内容、词级差异提示，删除分类前重复参数 schema。首项 TAIR 又反复检查至 150 秒超时（41 次模型请求），配对朴素组正常通过；因此中止，记录两次完整尝试及下一项部分日志，不是完整 21 题结果。
- **标准协议 a 轮**：修复 assistant/tool 对应关系后，三类重复任务恢复实际复用，已完成的产物多数正确。但新加的失败摘要在最新执行成功后仍重复显示“LATEST EXECUTION FAILED”，条件提示也未区分缺陷已经修好。区间、Unicode 任务均在多次检查成功后继续运行至 150 秒超时。发现这个实验引入的状态问题后中止；记录 35/42 次尝试及下一项部分日志，不报成完整 21 题成绩。
- **标准协议 b 轮（最终）**：修正上述当前/历史状态混淆，同时仅从模型上下文移除入表元数据，保留原始日志和 SQLite 学习行为。启动前确认引擎 running/waiting 都为 0；重新冻结全部 21 项，运行中不更改。所有失败原样归档。

## 方法

21 个自编任务：原 17 项回归，另四项为分块函数的补齐约束、SQL 的 NULL 分组过滤约束，各含 base 与 changed。新增 oracle 在任何该任务推理前先用参考实现和空实现校验，四组正例通过、四组负例拒绝。四题在 b 轮已运行，最终各题均应视为开发回归，不是外部独立泛化证据。

同一个 yuesheng 6×RTX 5090、DeepSeek-V4-Flash-Vision-Exp 服务，Pi 0.85.1。朴素组使用普通 tools 接口，允许多工具；TAIR 对外只有 plan，内部使用相同七个 Pi 原生工具，模板关闭、动态内容码表开启。两组整体输出上限 17408，TAIR 另有每子工具参数 2048 限制。朴素组仍连接同一带实验补丁的服务，并非另起未打补丁 vLLM。

同一任务恢复相同绝对路径和初始文件，状态分离，固定随机顺序串行配对，每题每组一次；相关任务按 base/repeat/changed 顺序。任务、源代码、顺序均在首次推理前冻结。每项 150 秒上限，无测试器自动重试；Agent 时间包含启动、全部请求、恢复、工具执行与最终回复，独立 oracle 不计入。

`passed` 是产物 oracle 通过且 Agent 正常结束；`closed` 再要求最后一次工具执行没有错误，两者都不等于所有过程要求已全面验证。例如运行失败测试是否严格先于其他动作，需要另查事件，不能仅由文件内容证明。失败的时间不剔除，未完整记录的用量不冒充精确总量。跨轮次耗时受模型输出变化影响，不是单变量因果证明。

## 最终结果

同一服务串行配对，共 21 题、42 次运行，每组每题一次。最终冻结的 42 份产物独立复验全部与原始 oracle 记录一致；没有超时或零工具执行。

| 指标 | 朴素 tools | TAIR plan + 动态码表 |
| --- | ---: | ---: |
| 产物通过且正常结束 | 21/21 | 20/21 |
| 上述通过且最后工具无错误 | 21/21 | 20/21 |
| Agent 总耗时 | 227.80 秒 | 262.84 秒 |
| 已记录生成 token | 22218 | 13179 |
| 输入 token | 243131 | 385737 |
| 分类控制记录（与生成分列） | 0 | 59 |
| 模型请求 | 87 | 59 |
| 工具错误 | 4 | 11 |

两组用量记录完整。TAIR 生成 token 减少约 40.7%，请求减少约 32.2%，但输入增加约 58.7%，总体慢约 15.4%。这些是本轮总量，不能推广为稳定性能倍数。分类控制记录不等于每次都在多个候选间分类：恢复模式可能只有通用分支。

**重复任务的复用成立，但时间收益很小。** 四项 repeat 均真实执行码表复用并通过产物验收。TAIR 合计 33.75 秒、1049 生成 token；朴素 34.11 秒、3319 生成 token。生成减少约 68.4%，耗时仅差约 1.1%，单次配对不足以证明稳定提速。

**一个明确的误复用。** `nullable_changed` 要求排除全 NULL 分组，同时保留含非 NULL 值但总和为零或负数的分组。TAIR 仍复用旧 SQL，未加入所需过滤；自测成功、工具无报错、正常回复，但独立 oracle 拒绝。这是候选适用性判断失败。五次实际码表使用中四次正确、一次错误，样本不能当作通用命中精度估计。入表成功也仍不代表需求正确。

**额外的过程违约。** `repair_failure` 明确要求先运行 `python3 check_calc.py`。TAIR 先读取文件，再修改 `calc.py`，最后运行检查，跳过了修复前的失败验证；朴素组先运行了失败检查。两组均未修改检查脚本、最终产物均正确。冻结的主指标仍按产物 oracle 加正常结束计分，因此不改写 20/21；但这不能称为 20 项全流程合规。此为定向事后审计，不是所有任务过程约束的完整评分。

**恢复得到改善，仍有额外成本。** 本轮区间与 Unicode 任务均能在检查成功后正常结束，未重现前轮成功后不断检查至超时的状态错误；TAIR 仍有 11 次工具错误，多于朴素的 4 次。不能仅凭本轮没有超时就宣称循环问题普遍解决，也不能拿跳过初始失败检查的 `repair_failure` 证明恢复更快。

TAIR 记录的 `generation_preparation` 合计 55.95 秒，`generation_http` 为 169.74 秒；余下约 37.16 秒包含启动、工具、码表及其他开销。准备阶段约占总耗时 21.3%。朴素组没有同粒度阶段计时，汇总为 `null`，不能按零成本比较。当前证据说明输出缩短被更多输入、准备与恢复开销抵消，尚不能精确归因各项净耗时。

## 判断与下一步

三项问题未全部解决：标准消息协议和当前执行状态已修正；真实复用恢复，但变化约束仍会误命中；减少生成和请求尚未带来端到端提速。隐藏或截断候选内容的试验降低质量，已回退。下一步优先建立可检查的复用适用条件与拒绝路径，再对候选输入及准备阶段做单变量消融；补齐执行顺序等过程验收，避免只检查文件结果。不能靠放宽 oracle 或剔除失败任务报告加速。

本轮仅改本地桥接与测试代码，没有修改或重启常驻 GPU 引擎。测试使用真实码表的只读快照和隔离学习状态，未清空用户日常码表；快照条目 ID 与哈希已记录，完整种子数据库仍在本地隔离状态中，因此证据不等于可脱离该状态完整重放的发布包。
