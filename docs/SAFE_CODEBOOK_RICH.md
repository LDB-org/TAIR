# 第二个真实仓库：Rich 完整 Agent 对照

2026-09-19，在 Rich v13.7.1、commit `7f580bdcf07a3b269a0e786b6a3aa9c804f393cf` 上测试当前 TAIR。源码与 MIT 许可证保留在本地评估记录中，不提交上游评估数据。

## 方法

沿用 CPython 实验的原生多工具、TAIR 混合规划关闭码表、相同 TAIR 开启保守码表三组。两个 TAIR 配置只差 `PIJIT_DISABLE_CODEBOOK`，均开启 `PIJIT_SAFE_CODEBOOK=1`。没有修改运行时或为 Rich 添加专用规则。

每组 16 次任务，共 48 次。两次独立重复均从空表开始，每次调用启动新的 Pi 会话。相同任务的三个配置使用相同绝对项目路径，状态及前缀缓存命名空间隔离，组别随机交错。暖轮恢复上游原始源码。没有导入 CPython 码表，因此验证的是实现能否在新仓库独立学习复用，不是旧条目跨仓库迁移。

| 任务 | 每次独立重复 |
|---|---|
| JSON CLI 默认缩进 | 首次 4、重复 4、新参数 6 |
| JSON CLI 短别名 | 首次 -I、重复 -I、新别名 -J |
| UTF-8 文件读取 | 一次，显式指定 Path.read_text 的编码 |
| 非法文件大小 | 一次，decimal 拒绝负数，保留其他行为 |

CLI 验收同时检查文件和 stdin、显式覆盖、公有 JSON 类默认值、未知选项和 AST 修改范围。UTF-8 验收关闭 Python UTF-8 模式与 locale coercion，并使用 C locale。文件大小验收检查负数、零、单数 byte、SI 单位、precision、separator，并保护 decimal 之外的模块 AST。所有无关源文件受保护。

独立 oracle 和参考修改不提供给 Agent，也不配置为运行时 `PIJIT_VERIFY_CMD`。Agent 自己运行检查，外部再统一验收。因此，未能完整绑定的通用编辑不能仅凭最终验收通过就自动学习。

Pi 0.85.1 和工具在本机 macOS 的隔离 Python 3.11 环境运行，经 SSH 请求 yuesheng 既有六张 RTX 5090 服务。沿用普通 tools API 原生基线、2048 token 回复上限和 120 秒任务上限。使用同一已打补丁服务，不是另起一个未修改的 vLLM。每次回复允许原生多工具输出，组内允许前缀复用。

完整计时包含进程启动、规划、工具、Agent 检查、恢复、最终回复及外部 oracle，不含夹具准备和后验审计。编辑 bridge 的内部计时单列，不含启动该 Python 进程的成本。所有失败、超时和缺失用量保留，不以成功重跑替换。

## 准备阶段校验

8 个输入变体均确认原始代码不满足任务、参考修改通过。首次预检中，等长的缩进修改被 Python 子进程的旧 `.pyc` 掩盖；为验收子进程显式设置 `PYTHONDONTWRITEBYTECODE=1` 后重新通过预检。失败预检保留为 `preflight-stale-pyc.json`，发生在正式模型调用之前。正式 Agent 环境原本已经禁用字节码写入。

Rich 及其完整上游测试套件没有安装或运行；项目夹具包含实际 rich 包源码和许可证。仅在隔离环境补齐 `markdown-it-py==3.0.0`、`mdurl==0.1.2`，保留实际环境清单。本轮结论限于这四类任务，不等于 Rich 全量兼容性验证。

## 正式结果

完整流程 **47/48** 通过；保存代码重新验收 **48/48** 通过。原生组一个 UTF-8 任务触发 120 秒进程时限，虽然最终产物正确且记录到了结束回复，仍按流程超时失败保留。没有重跑替换。

原生组已记录请求均有 usage，但因一次流程超时，整体 `usage_complete=false`；另外两组为 true。不把原生超时组的总量当成已保证完整的性能分母，也不把不同完成率的总耗时差宣称为等质量加速。

码表开关的总差只有 **1.404 秒（约 0.48%）**，第一轮开启组稍快，第二轮稍慢。更关键的是，两组都没有进入 compact_edit，全部通过普通 edit 完成修改。因此，本轮**没有任何码表提速证据**；这点不能被 TAIR 与原生组的时间差掩盖。

重复值、重复别名和新参数也没有触发学习复用。当前 Rich 布局被本地绑定器拒绝后，外层模型选择普通编辑；普通编辑输出不进入现有码表。

### 判断与后续

跨到第二个仓库后，普通编辑正确性保持，但现有码表入口未覆盖一种常见的 argparse 源码布局。此前 CPython 上的 8 次暖命中和局部收益依然成立，不能据此推广到所有 CLI 程序。

优先补齐 main guard 及相应词法作用域下的参数绑定识别，并保留唯一目标、接收者绑定和未重绑定检查；随后用本轮同样的任务重新对照。另需约束 Agent 的搜索范围，避免已知相对路径仍触发全盘扫描。本轮没有修改运行时或搜索策略。

336 项本地测试通过。服务启动时间、镜像、tokenizer 摘要、健康状态前后一致，临时隧道已关闭。结构化生成请求为零，没有分类旁路事件可作为本轮收益证据。原始数据和此前失败记录全部保留并校验。

## 路由覆盖诊断

Rich 的 JSON CLI 将 `parser.add_argument(...)` 放在 `if __name__ == "__main__":` 块中，`import argparse` 也位于该块。当前 `deploy/preset_edits.py::set_cli_keyword` 要求目标调用是函数或模块 body 中的直接语句，并要求模块顶层导入 argparse。它拒绝此源码布局；默认值和别名的本地路由都依赖这个检查。

针对上游原始源码及三个最小源码片段做只读诊断：

| 源码布局 | 默认值/别名可路由 | 直接绑定拒绝原因 |
|---|---|---|
| Rich 原始源码 | 否/否 | 非函数或模块的直接语句 |
| 顶层 import，参数在 main guard 内 | 否/否 | 非函数或模块的直接语句 |
| 函数内 import，参数为函数直接语句 | 否/否 | 缺少顶层 import argparse |
| 顶层 import，模块直接定义参数 | 是/是 | 无 |

诊断没有执行、替换或改写上游程序，也没有放宽生产校验。它说明当前受支持的 CLI 语法布局存在具体覆盖缺口；不能因为抽象上同为 argparse 参数修改，就假定都会进入可学习路径。单纯增加码表条目无法解决此前置路由问题。
