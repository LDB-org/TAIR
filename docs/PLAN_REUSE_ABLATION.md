# 通用 plan 与动态码表的三组消融

2026-09-20。本实验检验两个独立主张：在没有内容复用时，通用 plan 是否减少完整 Agent 成本；相同 plan 在热任务中开启动态码表，是否再获得净收益。

## 实现与方法

`PIJIT_PLAN_DISABLE_REUSE=1` 现在也作用于通用 plan：不提供内容或模板复用候选，但成功写入仍学习入表，正常执行 read/write/edit/bash/grep/find/ls。没有关闭 plan、工具执行或改成特定语言路径。没有采用前两轮退化的目录后置、仅复用分类选项。

新增 `--ablation --empty-book` 实验参数。三组为原生多工具、通用 plan 禁用复用、同一通用 plan 开启复用。两组 plan 使用独立空 SQLite 状态（未清空用户现有数据库），同组在任务间持续学习；不向关闭组提供学习内容，也不把该组生成的内容泄漏给开启组。

21 个既有自编回归任务：首次、重复、变更约束，另含已有文件修改和失败恢复；每题每组一次，共 63 次。每题随机交错组顺序，相关任务顺序保持。每次重建相同工作目录和初始文件，启动新 Pi 会话；码表保留，对话不保留。这里每类“首次”指该任务族的首次，只有整个序列开头的表为空，后续族可能检索到其他任务产生的内容。

Pi 0.85.1；模型是 yuesheng 6×RTX 5090 既有 DeepSeek-V4-Flash-Vision-Exp 服务，TP2/PP3。native 多工具与缓存开启，两条 plan 均使用本地 tokenizer 与会话 cache salt；模板关闭，输出总上限 17408、plan 每子工具参数限 2048。每任务 150 秒上限，无测试器重试。所有恢复、失败、工具和最终回复计入端到端耗时；外部 oracle 单独验收。新加超时后的空闲屏障：确认服务 running=waiting=0 再开始下一组，屏障耗时单列，不冒充任务耗时或剔除失败。

此对照可评价整个 plan 协议的净效果，仍不能把所有差异都归因于网络请求数量。开启和关闭码表会改变候选上下文与模型轨迹；这正是系统级码表净收益应包含的成本。

## 状态

首轮 `plan-reuse-ablation-20260920-a` 检查到启动脚本硬编码 `PIJIT_PLAN_DISABLE_REUSE=0`，覆盖显式关闭请求；中途停止，完整原始记录保留，不作为消融结果。已修复启动环境透传，并用真实 Node 启动链配合模拟 Pi 子进程覆盖开/关两种设置。实验器另检查每次实际 chat 日志中的 `plan_reuse_enabled` 与组别一致，配置不符或测试器异常则停止。

正式 B 轮从新的独立空状态重跑，全部 63 次运行完成，保存产物独立复验与原始 oracle 全部一致。实际配置检查覆盖关闭复用组 52 次 chat、开启组 71 次 chat，未出现启动设置被覆盖。关闭组入表 16 次、开启组入表 12 次，证明没有把“禁用复用”实现成禁用学习。没有任务超时，全部 usage 完整。

## 结果

| 指标 | 朴素多工具 | 相同 plan，禁用复用 | 相同 plan，开启码表 |
| --- | ---: | ---: | ---: |
| 正确且正常结束 | 21/21 | 21/21 | 19/21 |
| 完整耗时 | 292.37 秒 | 202.80 秒 | 324.86 秒 |
| 单任务耗时中位数 | 9.80 秒 | 9.05 秒 | 8.31 秒 |
| 模型请求 | 91 | 52 | 71 |
| 生成 token | 29530 | 13754 | 23838 |
| 逻辑输入 token | 287407 | 186709 | 557840 |
| 分类控制记录 | 0 | 52 | 71 |
| 工具错误 | 4 | 5 | 17 |

禁用复用的 plan 组本轮总耗时少 30.6%，请求少 42.9%，生成 token 少 53.4%。这些是完整协议对照，不能拆成单独分类内核或网络优化的贡献，也不能把逻辑输入当 GPU prefill 运算量。

长尾显著影响总量：原生 `intervals_changed` 用时 88.34 秒，plan 禁用复用为 23.61 秒。逐题比较，plan 在 12/21 项更快，配对耗时降幅中位数约 6.46%。仅作事后敏感性分析，同时排除这一对后，其余 20 对仍全部正确，原生 204.03 秒、plan 179.20 秒，少约 12.2%；主表仍保留该任务，不用剔除结果替代正式分母。单次开发回归样本不能证明生产稳定加速率。

## 动态码表的净效果

四项预定义重复任务全部正确：

| 指标 | 朴素 | plan 禁用复用 | plan 开启码表 |
| --- | ---: | ---: | ---: |
| 合计耗时 | 33.15 秒 | 37.00 秒 | 36.80 秒 |
| 生成 token | 3196 | 2721 | 2343 |
| 实际正确复用 | 0 | 0 | 2/4 |

开启码表比相同 plan 禁用复用只少约 0.53% 时间，生成少约 13.9%；不能称为稳健的热任务加速。`unique_repeat` 和 `totals_repeat` 命中，另两项重新生成且发生工具错误。非重复任务中，`totals_changed` 和 `nullable_base` 错误复用，正常结束却未通过独立 oracle。

`jsonl_changed` 更重要：开启组没有实际复用，但经历 19 次请求、9 次工具错误，耗时 142.37 秒；关闭候选的同一 plan 为 10.89 秒，朴素为 13.72 秒。候选上下文可能影响重新生成和恢复，不能把全部坏结果归为执行了错误缓存。一次轨迹差异尚不能确立普遍因果关系，但足以否定“只要没命中就没有码表成本”。

开启组中位耗时更低，却总耗时更高、正确率更低，不能只展示中位数。累计命中的 KV token 较多也不能代替总体收益判断。

## 下一项优化的测量依据

禁用复用组 52 次模型请求中有 21 次最终回复，请求 HTTP 累计 49.27 秒、生成 3716 token。该 49.27 秒不是可无条件全部省掉的时间，也没有证明每次最终检查都冗余。

待验证方向：在原始 plan 请求里允许生成“全部执行成功后的简短回复”，只在所有步骤成功、没有待解释的新结果、且仍对应同一用户任务时发送；其余情形继续现有循环。这样减少额外收尾请求，保留读取未知信息、失败恢复和新用户输入的边界。本轮尚未实现或测量该路径。

本轮新增的运行时改动是正确兑现禁用复用开关，默认仍开启动态码表；没有把关闭码表当成最终产品方案。通用 plan 的净收益已在本轮出现，可靠的动态复用增益仍未建立。
