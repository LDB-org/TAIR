# 精确修改候选内容的实验：未保留运行时改动

2026-09-20。尝试在默认关闭的复用核对协议里增加精确 edits：模型可输出 oldText/newText
列表修改已有内容；每次匹配必须唯一，拒绝空/多重/不存在的匹配，按顺序展开成普通 write。
仍保留完整生成，不增加请求或工具数量。实验代码及提示完整冻结在本轮 sources 中。

在既有 DeepSeek-V4-Flash-Vision-Exp、6×RTX 5090 TP2/PP3 上，用指定单候选的组件探针
测试两类 SQL 的适用/变更约束条件，原协议与核对＋edits 两组，共 8 次请求。每次一个
分类控制，usage 完整；使用已补充正数分组的 oracle，全部保存内容再次独立验收。
这不是自然分类或完整 Agent 性能测试。

| 条件 | 原协议正确 | 核对＋edits 正确 | 核对组实际选择 |
| --- | --- | --- | --- |
| 汇总原要求 | 是 | 是 | 原样复用 |
| 汇总仅保留正数 | 否 | 是 | 完整生成替代内容 |
| NULL 分组原要求 | 是 | 是 | 原样复用 |
| 排除全 NULL 分组 | 否 | 否 | 完整生成替代内容，错误排除了正数 |

核对组仍为 3/4，原协议 2/4。两次不适用候选均被拒绝，但精确修改分支采用次数为零。
核对组四项分别生成 71、121、89、135 token，请求准备＋推理耗时约 1.18、1.61、1.40、
1.74 秒；没有证据说明新增 edits 减少生成或耗时。候选源文本很短，这次未采用也不能
推导出长内容场景绝无价值，但不足以支持继续增加运行时分支。

因此撤回本轮 edits schema、解码器及专属测试，保留此前默认关闭的核对功能。运行时
两个变更文件与上一轮 probe 保存的源码逐字一致；用户现有修改未回滚，所有失败证据
和实验源码保留。临时实现的 507 项测试通过，恢复后的完整 502 项测试通过；归档校验
62401 条通过，2853 个导入文件保持一致。无服务重启、无用户码表清空。

这次实验指出：仅增加一种输出格式不会保证模型采用它，拒绝错误缓存后重新生成仍可能
误解同一约束。后续工作需要验证实际采用率和行为正确性，不能以新增开关数量代替收益。
