# First-tool classification and warm codebooks

2026-09-21. `--first-tool-reuse-ablation` adds a four-arm comparison: native Pi; ordinary plan with reuse; general plan without reuse; general plan with reuse. General plan sets `PIJIT_FIRST_TOOL_CLASSIFICATION=0`, retaining codebook candidates and general generation but removing native first-tool choices. Both reuse arms use the same candidate limit, retrieval rules, content binding and admission implementation. All other optional interventions are off. This isolates first-tool selection among the two reuse arms, and reuse among the two general-plan arms.

Frozen run: `first-tool-reuse-ablation-20260921-a`. Each language has one base task, two identical repeated requests and one changed requirement. Python JSONL changes duplicate-key handling; JavaScript deduplication changes case sensitivity. Each arm retains its own isolated initially empty book across tasks, while its workspace files reset before each task. User books are untouched. There are eight tasks per arm and 32 full-Agent runs, interleaved using seed 731.

Pi 0.85.1, local pinned tokenizer, existing DeepSeek-V4-Flash-Vision-Exp service (TP2/PP3), concurrency one. A read-only hardware check during this run confirmed six RTX 5090 GPUs and driver 610.43.02. No model/service deployment or restart. Native keeps its ordinary multi-tool/prefix-cache path; this is not a patched-versus-unpatched vLLM kernel comparison.

Final correctness and initial reused-content correctness must remain separate. A whole plan may fail after a successful cached write; the old whole-plan reuse counter then stays false. Conversely, final correctness may follow a wrong cached write and later repair. The content audit correlates each actual completed write with its request ID and selected/reused IDs, verifies its hash against the frozen final book, and independently tests the first-written primary-file bytes before repairs. It is limited to these standalone JSONL/JavaScript fixtures and records missing coverage explicitly.

Ordinary plan's two timeouts make its totals unsuitable for a clean equal-quality speed ratio.

## Repeated requests and changed requirements

On four repeated tasks, general plan with reuse takes 23.299 seconds and 1336 generated tokens versus 43.335 seconds and 3312 tokens without reuse. Native takes 32.897 seconds and 3273 tokens. The four cached writes all match selected entry IDs and frozen source hashes, and all four first-written contents pass independent oracles before any repairs. The repeated-task observed savings versus the no-reuse control are 46.2% wall time and 59.7% generated tokens. The control also incurred four JavaScript command errors, so the time difference includes different check/recovery trajectories, not just eliminated source generation.

More repeats are not monotonically faster: JSONL cached repeats take 6.385 then 5.791 seconds; JavaScript takes 5.085 then 6.038 seconds.

Changed requirements take 29.331 seconds with reuse versus 29.216 without, and 19.852 for native. General-plan reuse selects the old JSONL candidate but abandons actual reuse; its newly generated first implementation still accepts duplicate keys and needs correction. The no-reuse general plan also generates that defect. On changed JavaScript requirements, general-plan reuse actually writes the old case-sensitive implementation, fails its check and repairs it. Its 8.736 seconds compares with 5.956 without reuse.

Across all five actual content reuses in the new path, four are initially correct and one is wrong. Final 8/8 correctness must not be described as perfect cache correctness. Ordinary plan's two actual cached writes both occur on changed requirements and both fail the first-content oracle before repair; it does not perform any actual cached write on repeated tasks in this run. Identical generated bytes alone are not counted as reuse.

## Long-tail failures and diagnostics

Ordinary plan `unique_base` and `unique_repeat` reach the 150-second task limit without executing any tools. Each first HTTP request returns 500 after generating 17408 tokens; the following request is cancelled at the task deadline. Accounting is incomplete, hence lower-bound usage above. Recorded post-timeout barriers confirm backend idle before the next task. The second identical JavaScript repeat later completes normally. This does not prove that removing native branches universally prevents the long tail.

The client previously discarded the server error response's request ID, selected wire index and finish reason. After freezing this experiment, error telemetry now retains `engine_request_id`, `engine_decision_index` and `engine_finish_reason` alongside existing usage/budget fields. It does not add a model request, change exception handling or log generated source. A simulated length failure verifies retention without marking incomplete usage complete. Those fields cannot retrospectively recover the discarded details from this run.

Validation: all 32 final artifacts rechecked against recorded outcomes; 22 first completed relative primary-file writes audited across 24 plan tasks (the other two executed no tools). 591 tests pass after the diagnostics change.
