# 分类后的执行与结束出口

2026-09-20，工作区实验版本。此报告完整回归对应 `general-continuation-paired-20260920-c`，最后的循环保护单独验证于 d 轮；结果见同名 JSON 汇总。

## 改动

此前，末尾“回复”分类分支只能生成 `{content}`。模型即使意识到还要写文件或修复错误，也无法从该分支返回工具调用。现在该分支可以生成原生 `{steps}` 或最终 `{content}`。

反向出口同样必要：所有指定首工具及内容复用分支也允许最终 `{content}`。分类结果作为行动建议，后续生成可根据已完成的执行和检查结果结束，避免错误分类强制重复工具调用。各分支仍严格校验 JSON schema；不能同时返回 content 和步骤，也不能调用未注册工具。

工具报错后，本次用户任务的剩余轮次进入通用重新规划：只保留可生成任意合法原生步骤或最终回复的分支，暂不选择首工具或复用内容。期间成功读取文件不会立即退出恢复状态；下一个用户任务恢复正常分类。这不判断错误来自源码还是测试，也不把失败改成成功。恢复请求仍调用 fused endpoint，只有一个分类候选，不应称为有效的多候选分类加速。

仍然只有一个外部 `plan`，选择和后续生成使用同一引擎请求，没有加入额外 verifier 模型。失败后修复、何时完成仍由模型判断；这些出口不是语义正确性证明，也不保证消除所有循环。

## 保留的失败试验

`general-continuation-paired-20260920-a` 只加入“回复→执行”出口。JSONL base 通过，但 repeat 虽成功复用，却反复运行同一条已成功检查，150 秒超时，记录到 34 次请求。超时请求的用量不完整，不能作为完整费用统计。两项 native 配对完成；随后人工中止该试验，另一个正在运行的 case 只有部分日志。它不是完整 17 题成绩，证据及校验清单原样保留。

随后增加所有分支的结束出口，重新冻结 b 轮。朴素 17/17、187.919 秒；TAIR 15/17、361.551 秒。TAIR 虽没有零工具执行任务，但 JavaScript changed 自写检查重复失败 9 次，intervals changed 重复失败后超时（24 次工具错误）。后者文件功能通过，Agent 未正常结束，按原规则计失败。SQL changed 仍误复用。TAIR 仅记录到生成 token 14758、输入 793202、分类 70，用量不完整，不作为精确总费用。34 份产物复验与原 oracle 一致。

因此 c 轮再加入失败后的通用重新规划，重新冻结并运行全部 17 项配对。各轮从原用户码表的新隔离快照开始，不沿用前一轮新增条目。未重启或修改 GPU 服务，未清空用户码表。

## 方法

原 14 题现在是开发回归集。另加入修复已失败的 Python 测试、CSV 汇总、Unicode casefold 去重三题；任务及 oracle 在 a/b 两轮推理之前写好，未根据新题输出调整。新题参考实现与空实现分别全部接受/拒绝，检查运行于 a 轮开始后、新题实际执行前。c 轮已经观察过三题在 b 轮的结果，因此最终 17 题均属于开发回归；不能把它们当作 c 轮的独立泛化证据。它们只是有限自编用例，不是外部独立基准。

17 题各运行朴素 Pi/vLLM 多工具组和 TAIR plan 组，各一次，同一 yuesheng 6×RTX 5090 / DeepSeek-V4-Flash-Vision-Exp 服务，Pi 0.85.1。朴素组允许多工具；TAIR 模板关闭、动态内容码表开启。与前轮相同，输出总上限 17408，TAIR 每子调用另限 2048；相同工作路径和初始文件，分离状态，同题固定随机顺序串行配对。两组使用同一个带实验补丁的服务、不同 API 路径，不是另起无补丁服务。

Agent 时间包含启动、全部请求、执行、恢复及最终回答；独立验收不计入。150 秒超时，失败不剔除、不自动重试。源码、任务与顺序在调用前冻结，运行中不更改；运行后重复验收全部保存产物。生成 token、分类控制、输入 token 分列。

按原有产物与结束口径，原 14 题从初始 5/14 变为 14/14，新增三题也通过；原 14 题已用于调优，不是独立泛化提升。34 份产物重新验收一致。没有零工具执行任务。TAIR 生成量少 12.5%，但总耗时多 65.5%，不能声称总体加速。

**17/17 不代表完整流程可靠。** JavaScript changed 和 intervals changed 均未重新跑通最后的自写检查；前者 16.793 秒、3 次工具错误，后者 93.557 秒、20 次工具错误。模型最终解释自写断言有误，但没有实际修正并重跑。额外的流程收尾指标因此是 15/17，仍不是全面语义验收。

另外，c 轮 SQL changed 没有复用旧查询。base 的检查先失败，恢复后只有 bash 成功，没有重新将早先写入的内容入表；候选历史因此与 b 轮不同。不能把此次 SQL 通过归因于语义命中问题已被修复。恢复策略、候选积累和模型运行波动交织，未做单变量重复统计。

## 最终循环保护及定向验证

c 轮后增加确定性的失败循环保护：同一用户任务内，同一个 plan 参数连续失败两次（初次加一次重试），第三次相同计划拒绝执行，返回明确错误，保持任务未完成。参数改变、中间执行其他计划或新用户任务会重置连续计数；不会把普通重复读取一概缓存或禁止。此保护不能识别变换写法的循环，也不自动修正错误逻辑。

最后修改后运行全部 432 项单元测试。另冻结 d 轮，对 JavaScript changed、intervals changed、repair_failure 三项做配对定向验证。d 轮是独立 seed 快照和子集顺序，没有预先运行各族 base/repeat，候选状态不同；不可拿三项耗时直接替换 c 轮行来拼成虚构完整成绩。最终带保护版本没有重新跑全部 17 项。

d 轮两组均 3/3 通过，六份产物复验一致，最后一次工具执行均无错误，用量完整。TAIR 合计 36.254 秒、生成 1803 token；朴素组 43.258 秒、生成 4408 token。TAIR 有两次工具错误并恢复；没有发生连续两次相同计划失败，因此运行中未触发新增循环拒绝，不能把该子集耗时差归因于保护。确定性拒绝、允许一次重试、变更动作与新用户任务重置均有单元测试覆盖。

最终结论：从零执行提前结束到实际完成产物已有明显改善；恢复路径可处理部分错误，未证明普遍可靠。没有总体提速证据。语义误复用、检查收尾和失败后的学习仍需独立测试；17 项有限开发回归不能证明通用工程成熟。
