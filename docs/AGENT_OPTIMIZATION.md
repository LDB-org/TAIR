# 完整 Agent 外层优化（2026-09-19）

这轮让明确的编辑要求更稳定地进入码表路径，并减少重复分词和目录误读恢复。
**重复测试中总耗时小幅下降；暖轮更快，冷启动仍有额外成本。**

## 改动

- 明确 CLI 修改在成功读取源码后，由现有本地路由调度；同文件最多八个独立句子合并编辑。
- 已调度过的批量任务按原句记录，失败也不会自动重复调度；Schema/精确重放模式保持单项调用。
- 测试配置启用已有的 tokenizer revision 缓存、continuation 缓存和目录读取修正。
- 内层仍按“分类候选 → NONE 时生成 → 校验后入表”执行，未开启预设执行或零模型重放。
- 修复汇总脚本漏列新增组名的问题；额外保存完整任务判定，任务失败或用量不完整时返回非零状态。

配置仍为 opt-in，使用方式见 [Pi 配置说明](../integrations/pijit/README.md#outer-loop-preparation-and-directory-reads)。
运行时 revision 必须对应实际部署的 tokenizer 和 chat template。当前会话仍会实时分词。

## 完整任务复测

5090 环境、Pi 0.85.1、同一 vLLM 后端。三个场景：多属性修改、别名、函数修复并补测试。
两次独立重复，每次包含冷/暖轮，各组 12 个任务，总计 36 个。各组交错执行。
暖轮恢复初始源码，保留本组码表和分词缓存；不保留对话。计时包含启动、工具、测试、恢复、回复和独立行为检查。

相对朴素组，总耗时下降 **1.8%**；暖轮下降 **13.3%**，冷轮增加 **9.9%**。
两次独立重复的优化组分别为 64.02、64.29 秒，朴素组为 65.54、65.08 秒。
中位任务耗时为 9.42 对 9.33 秒，因此总耗时的小优势不等于每个任务都更快。
别名场景合计仍略慢于朴素组。

上一配置有一次修好函数却没有按要求补测试，已判失败且保留原耗时；不能把这次较短耗时当作完整工作。
英文报告另外列出双方都完成任务的配对比较。报告中的 `final-result.json` 才是附加测试完整性检查后的最终判定。

分词 HTTP 请求从上一配置的 975 次降到 245 次。这不是模型推理请求数；本地调度也不是零模型编辑。
外层推理、模型输入及普通工具仍占主要成本，不能把 token 节省直接换算成速度提升。

## 证据与边界

- [正式英文报告、逐任务记录和源码快照](../results/experiments/codebook-outer-agent-20260919-b/REPORT.md)。
- [18 任务先导轮](../results/experiments/codebook-outer-agent-20260919-a/REPORT.md)：优化组 62.38 秒，朴素组 69.81 秒；不与正式重复轮混算。原汇总漏列新组的文件保留，另附修正版。
- 282 项仓库测试通过；正式轮 146 个分类请求全部找到引擎 sampler-bypass 记录。
- 全部 36 个保存下来的项目通过独立 unittest 复跑；这不抹去上一配置漏补测试的任务失败。
- vLLM 版本 `0.28.1rc1.dev137+g5ab628dd1`，服务启动时间仍为 `2026-09-18T05:44:43.699377485Z`；未重启、替换部署或修改权重。

这些是共享后端上的少量手写任务，1.8% 的总耗时差不足以证明稳定的普遍加速。
本轮同时调整路由和传输，收益不能全部归于码表。码表仍仅在编译校验后入表，行为正确性由后续任务检查验证。
朴素组使用同一已打补丁服务的普通接口，并非另起未打补丁 vLLM。

下一步最值得投入的是冷启动分词校准成本、更广的编辑意图识别和跨文件真实任务流；已有结果并不能证明无限持续“越用越快”。
