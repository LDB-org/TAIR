# 本地 tokenizer 准备优化与复测

2026-09-20。只优化客户端准备，不修改分类提示、候选内容、计划 schema、码表准入或模型权重。未安装引擎补丁，未重启常驻 GPU 服务，未改变引擎随机 cache salt。本轮不进行 SFT。

## 实现

桥接新增显式启用的本地文本 tokenizer。使用从实际部署只读取得的 tokenizer.json 与 DeepSeek V4 renderer，逐个校验文件 SHA-256、快照 manifest SHA-256 和客户端 tokenizers 版本。模型权重不下载，快照保留原许可证且留在仓库外。模块只处理当前不启用 thinking 的文本消息及标签，其他形状保留原服务器路径；没有将一般工具调用改成任务专用规则。

`PIJIT_LOCAL_TOKENIZER` 指向可信快照，`PIJIT_TOKENIZER_REVISION` 固定其 manifest 摘要。`PIJIT_LOCAL_TOKENIZER_VERIFY=1` 时所有本地计算仍与远端逐 token 比对，不一致立即终止，不能发送有差异的推理输入。正式计时关闭远程比对；现有固定标签缓存也由 revision 启用。每个桥接进程仍有 CPU tokenizer 加载成本。默认配置继续使用服务器，不擅自修改用户 Agent 配置。

该快照仅用于本次 DeepSeek V4 部署，其他模型继续走原路径；这不是通用 tokenizer 替代品。文件哈希不能自动检测远端部署变更，部署更新后必须重新取得快照并核对。

## 环境与方法

yuesheng 6×RTX 5090，DeepSeek-V4-Flash-Vision-Exp，vLLM `0.28.1rc1.dev137+g5ab628dd1`，Pi 0.85.1；客户端 CPU 在本地 Mac，`tokenizers==0.22.2`，经 SSH 转发连接同一服务。部署 tokenizer mode 为 deepseek_v4。快照 manifest SHA-256：`d85549f9a50eb0c21b39f3eabcc84d109d49ed68b86117e437fda5359a10ae2d`。启动前确认服务 running/waiting 均为零；不是为每个样本独占或清空服务缓存。

用户码表只做 SQLite 只读快照，实验在独立 state 中持续学习，不清空用户日常码表。快照元信息、代码、任务顺序及原始结果归档，完整 tokenizer 快照和种子数据库仍在仓库外。

## 一致性验证与固定输入结果

五个任务（JSONL base/repeat、失败修复、SQL NULL base/changed）的配对运行共十次，产物验收 10/10；其中 TAIR 全部 154 次本地 tokenization 与远端逐 token 相等。这是正确性核对模式，不能把其耗时当作优化后的耗时。

另做三个固定上下文，每个五次配对：短中英文需求、长候选源码、标准 assistant/tool 历史。每次有 15 个分支；顺序固定随机化，生成的完整 prompt IDs、continuation IDs 和分类标签逐项比较，15/15 相等。每次本地尝试清除 tokenizer 对象缓存，包含快照加载，但不包含新 Python 进程启动；此测试没有 GPU 推理。

| 准备指标 | 原远程路径 | 本地路径 |
| --- | ---: | ---: |
| 配对样本 | 15 | 15 |
| 中位数 | 0.7775 秒 | 0.1171 秒 |
| 合计 | 15.0473 秒 | 1.9187 秒 |
| 远程 /tokenize 请求 | 465 | 0 |

合计准备时间减少约 87.2%，中位数减少约 84.9%。这里只证明准备阶段收益，不是模型吞吐或完整 Agent 加速倍数。短任务收益与客户端 CPU、网络 RTT 和候选数有关，不能推广成服务器本地部署下的同等收益。

## 完整 Agent 配对

21 个既有自编开发回归任务，共 42 次运行；两组同模型、同七个原生工具、同工作目录/初始文件，串行随机交错。朴素走普通 tools，TAIR 只暴露 plan，动态内容码表开启，模板关闭。两组输出上限 17408，TAIR 每子工具参数 2048。超时 150 秒，不自动重试。Agent 时间包含进程启动、全部推理、工具执行、恢复及最终回复；独立 oracle 不计入。朴素连接同一实验补丁服务，不是另一台 pristine vLLM。

主指标为产物 oracle 通过且 Agent 正常结束，不代表所有过程指令都已验证。原失败题保留，没有挑选成功任务计算总耗时；本轮任务都是已见开发回归，不能当作外部泛化验收。

测试完成，42 份保存产物独立重跑 oracle，与原记录全部一致；没有超时或零工具执行。两组用量记录完整。

| 指标 | 朴素 tools | TAIR 本地准备 |
| --- | ---: | ---: |
| 产物通过且正常结束 | 21/21 | 20/21 |
| 上述通过且最后工具无错误 | 21/21 | 20/21 |
| 总耗时（含失败项） | 215.27 秒 | 192.24 秒 |
| 生成 token | 21016 | 10762 |
| 输入 token | 235423 | 362835 |
| 分类控制记录 | 0 | 55 |
| 模型请求 | 85 | 55 |
| 工具错误 | 2 | 9 |

TAIR 本轮总用时少约 10.7%，生成 token 少约 48.8%；但质量为 20/21 对 21/21，不能声称相同质量下的全面加速。输入仍多约 54.1%。55 条分类控制记录包括恢复模式的单一通用分支，不代表 55 次多候选语义分类。

四项 repeat 均正确复用：TAIR 合计 25.30 秒、1149 生成 token；朴素 31.94 秒、3128 生成 token。此小子集两组均 4/4，TAIR 本轮耗时少约 20.8%、生成少约 63.3%。这是每题一次的开发回归子集，没有统计置信区间，不推广成稳定通用加速率。

**失败保留。** `nullable_changed` 又复用旧 SQL，未排除全 NULL 分组，自测成功而独立 oracle 拒绝；TAIR 此项 6.51 秒，朴素 12.86 秒。五次实际复用中四次正确、一次错误，不能用错答更快证明有效加速。`intervals_changed` 虽最终正确，仍经历五次工具错误。此次 `repair_failure` 两组都先运行了要求的失败检查，检查脚本原样保留；这只审计该项执行顺序，不代表所有过程指令已覆盖。

**实际准备成本。** TAIR 共完成 672 次本地 tokenization、零次远程 `/tokenize`。准备阶段总计 10.50 秒，模型生成 HTTP 阶段 149.35 秒，其余约 32.39 秒包含启动、工具、码表、能力协商及其他开销。`generation_http` 不是纯 GPU kernel 时间。朴素缺少同粒度阶段计时，记为 null。

前轮 TAIR 为 262.84 秒、准备 55.95 秒、59 次请求；本轮为 192.24 秒、准备 10.50 秒、55 次请求。两轮同一 24 条种子快照（摘要 `daeb1b30ffb2b924b5c3de105e4b67f4501e9218a63bd548df838ca1a4fd7b84`），但模型输出和恢复轨迹不同，绝不能把两轮全部时间差归因于准备优化。能够直接归因的证据是上面的固定输入逐 token 等价配对。

## 结论与剩余工作

本轮已证实：把部署一致的 tokenizer 移到客户端，可消除多路远程 tokenize，并实测降低准备耗时；不需要训练模型。完整 Agent 的观察总耗时也下降，但误复用依然存在，尚未达到与朴素相同质量的通用提速。

引擎随机 cache salt、候选输入体积、重复错误恢复仍未改变。下一步应分别验证会话级 KV 前缀复用，以及带困难负例的选择/拒绝行为；是否使用 SFT 应由后一项在独立任务上的质量改善决定，不能靠训练替代本轮已定位的传输优化。

446 项单元测试通过；完整档案校验及 git diff --check 通过。改动未提交，未修改用户 Agent 默认配置。
