# 动态码表候选被重复内容挤占的修复

2026-09-20。通用内容码表此前先获取相关性最高的 15 条记录，再按完整内容去重并截断。
同一内容在不同历史请求下可以多次入表，因此前 15 条可能全部对应同一内容，排名更靠后
的不同内容永远进不了本次分类目录。表越大不意味着有效候选越多。

现在 SQLite 仍按原有相关性、复用次数和时间排序，客户端逐行读取，收集到请求数量的
不同内容后停止。保留最高排名的代表条目、已有版本和拒绝过滤、内容完整性检查。
普通 PlanBook 默认检索行为不变，ToolContentBook 使用此路径。不删除历史记录，不改变
分类分支上限，不绕过模型选择，也不把相同内容或历史执行成功当作语义正确证明。

回归测试构造 30 条重复内容记录和一条较早的不同内容：旧查询的前 15 条均重复，
新查询能返回两个不同内容；同时覆盖数量限制、代表条目排序和拒绝后替换代表条目。

本地合成 SQLite 压力检查，每组顺序读取十次，以下为中位数。只有首条内容不同，
其余内容重复；contract 为等长的 `write file variant NNNNN`，查询 `write file`，
要求两个不同内容。内容是短文本，未代表大型真实源码数据库。

| 记录数 | 旧路径耗时 | 新路径耗时 | 不同候选数，旧→新 |
| ---: | ---: | ---: | ---: |
| 31 | 0.217 ms | 0.194 ms | 1→2 |
| 1000 | 0.872 ms | 1.979 ms | 1→2 |
| 10000 | 6.831 ms | 27.259 ms | 1→2 |

这是修复候选遗漏，不能宣称 GPU 推理或任务端到端更快。大量重复记录需要遍历更多行；
SQLite 排序也并非恒定成本。没有在本轮增加无证据的语义阈值或关闭动态码表。
下一步需要真实 Agent 对照：正确复用次数、生成量、候选输入成本和完整耗时一起验收。
此前自然语言变更导致错误复用的问题尚未解决。

全套 485 项测试通过，归档校验通过（2853 个导入文件，60996 个原始校验条目）。
本轮没有运行 GPU 推理、重启服务或改动用户码表。

## 后续修复：先过滤显式内容，再限定候选数量

同日继续检查发现，bridge 在取出并合并有限候选后才执行 `compatible_payload`。
当用户给出明确代码块时，靠前的不匹配条目被剔除，较后的完全匹配内容却不会补位；
模板也可能先挤掉普通内容，随后自己因内容不一致被排除。

已有的显式内容检查现在作为检索条件执行，达到合格候选数量后才停止。模板与普通
内容各自过滤后再合并，最终分类数量上限保持不变。没有指定内容代码块时仍使用
原有语义选择路径，没有引入关键词决定复用或额外模型请求。
`payload_mismatch_candidates` 现在统计检索中检查并排除的记录数，不再只统计
旧的截断目录；相同内容的多个被排除记录可能分别计数。

新增四个 bridge 回归案例：普通内容/模板分别覆盖存在匹配和完全没有匹配两种情况。
每例包含 20 条不匹配内容；存在匹配时将唯一匹配条目排在较早入表的位置，仍能进入
真实的 plan 解码路径，展开逐字正确的内容。分类选择由测试桩提供，因此证明的是
候选筛选和展开正确，不是实际模型命中率。无匹配时目录为空，继续生成/回复路径保留。

全套更新为 489 项测试通过，归档校验仍为 60996 条通过。上述本地压力耗时是上一版
去重修复的测量，不代表新增过滤后的性能。本次仍未运行 GPU 端到端对照；自然语言
约束的错误复用和新增遍历成本仍需实测。
