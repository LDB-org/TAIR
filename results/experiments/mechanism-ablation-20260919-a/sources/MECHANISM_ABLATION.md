# 单机制消融测试

本轮使用当前修复后的代码，将编辑内部与完整 Agent 分开测量。
不重启或修改模型服务；所有正式失败、恢复、冷缓存填充成本保留。

## 完整 Agent 配置

统一基线 `base` 使用紧凑工具客户端、并行准备，关闭码表及所有可选优化。
每个处理组只改变对应父组的一个配置值，程序测试校验此条件。

| 处理组 | 对照父组 | 唯一变化 | 测量目的 |
|---|---|---|---|
| serial | base | 串行准备开启 | 反向测量准备重叠的收益；serial 是关闭并行的处理组 |
| labels | base | 设置经现场核验的 tokenizer revision | 启用分类标签 token 缓存 |
| continuation | labels | continuation cache 开启 | 在标签缓存基础上单测工具续接 token 缓存 |
| codebook | base | disable codebook 关闭 | 单测动态编辑码表 |
| routing | codebook | local routing 开启 | 在码表开启时单测明确请求的本地路由 |
| directory | base | directory guard 开启 | 单测目录读取纠正 |
| batch | base | batch tools 开启 | 单测批量计划模式 |
| context | batch | plan context 开启 | 单测修复后的上下文规划约束 |

额外的 `native` 使用同一已打补丁服务的普通 tools API，作为参考，不计为单因素边。
未启动独立未打补丁的 vLLM。native 保持 `parallel_tool_calls=false`。
批量模式同时改变工具目录、提示和决策粒度；因此其结果是该实现开关的整体效果，
不能进一步归因为“只少几次 HTTP”或者纯分类算子的收益。

六类任务：多属性修改、别名添加、函数修复并添加测试、JSON 配置、带引号及嵌入
换行的 CSV、包含 80 个无关模块的项目导航。每种配置、每类任务冷暖各一次，
共 120 次完整 Agent。固定随机顺序；每个配置/任务单独建立状态，暖轮恢复相同
绝对路径的原文件，保留运行时缓存，重新启动会话。没有预置正确编辑或重试替换样本。

计时包含 Pi 启动、规划、模型及工具调用、任务测试、恢复、最终回复和独立行为检查。
初始文件恢复与后验审计不计入任务耗时。原测试完整性检查和请求新增测试的变异审查
分开记录，后者不覆盖原始结果。生成 token、分类控制记录和输入 token 分列。

## 编辑和服务层对照

- 18 次理想分类/生成对照：三个输出规模各三对。动作预先绑定，测量服务阶段和
  HTTP 时间；离线准备和单独存档的两个 warmup 不在正式计时内，不代表一般编程任务。
- 63 次普通编辑/紧凑生成/动态码表对照：七种情境、三次重复、三个组。
  包含首次生成、复用、参数变化、表述变化及源码变化。所有组执行相同行为检查。
- 54 次生成/schema/schema+JIT 对照：三类编辑、三次重复、冷暖两轮、三个组。
  在暖轮恢复相同源码，验证真正生成后入表的精确回放。

这些层次解决不同问题，不把微基准收益直接套到完整 Agent，也不累加百分比。
预设/schema 路径和码表路径存在替代关系，不强行排列成一个全部开启的总开关。

## 解释原则

先检查成功率，再看耗时；快速失败不能计为等量工作加速。除总体时间外，报告
冷暖轮、每类任务和机制实际触发次数。功能没有触发时，不把时间差当作该功能收益。
失败后额外调用与耗时包含在原配置中；不单独扣掉后再声称提速。

这是共享后端上的开发任务消融，每类仅一对冷暖 Agent 样本。结果可用于定位开销
和筛选配置，不能据此证明生产环境稳定加速或高置信度泛化。每条边的效果依赖父组，
不能认为它在任意组合下都会保持相同比例。

## 复现

使用隔离 Python 环境和 Pi 0.85.1，将 `PIJIT_URL` 指向兼容的现有服务。
模型和 tokenizer revision 必须现场核验，输出路径必须是新目录。

```sh
python benchmarks/benchmark_mechanism_ablation.py \
  --url http://127.0.0.1:8000 \
  --tokenizer-revision '<tokenizer.json SHA256>:<tokenizer_config.json SHA256>' \
  --out results/experiments/NEW_AGENT_ABLATION --timeout 120 --repeats 1
```

本轮的微基准命令、临时 SSH 隧道生命周期及现场版本由
[runner.py](../results/experiments/mechanism-ablation-20260919-a/runner.py) 记录。
最终结果见 [REPORT.md](../results/experiments/mechanism-ablation-20260919-a/REPORT.md)。

## 本轮结果（2026-09-19）

全部 255 次正式测试完成：18 次理想分类、63 次编辑对照、54 次精确回放对照、
120 次完整 Agent。前三组 135/135 通过；Agent 101/120 通过，无超时，用量均完整。
服务端 668 个分类请求均找到 sampler-bypass 证据，运行前后版本、tokenizer 和容器
启动时间一致，运行时代码哈希未变。

### 完整 Agent 的单因素变化

每组 12 次任务，以下是包含失败的总耗时观察值。成功率不同的组不能视为等量工作；
相同成功任务子集另列在原始报告，不替代全部结果。

| 启用机制及对照 | 对照 → 启用后 | 耗时变化 | 通过数对照 → 启用后 |
|---|---:|---:|---:|
| 并行准备：serial → base | 151.57 → 132.09 秒 | 省 19.49 秒，12.9% | 10 → 9 |
| 标签缓存：base → labels | 132.09 → 125.25 秒 | 省 6.84 秒，5.2% | 9 → 10 |
| 续接缓存：labels → continuation | 125.25 → 126.39 秒 | 多 1.15 秒，0.9% | 10 → 10 |
| 动态码表：base → codebook | 132.09 → 135.72 秒 | 多 3.63 秒，2.7% | 9 → 10 |
| 本地路由：codebook → routing | 135.72 → 123.81 秒 | 省 11.91 秒，8.8% | 10 → 10 |
| 目录纠正：base → directory | 132.09 → 126.46 秒 | 省 5.63 秒，4.3% | 9 → 10 |
| 批量计划：base → batch | 132.09 → 106.99 秒 | 省 25.10 秒，19.0% | 9 → 10 |
| 上下文约束：batch → context | 106.99 → 95.08 秒 | 省 11.91 秒，11.1% | 10 → 10 |

朴素组是 **12/12、164.53 秒**，base 是 **9/12、132.09 秒**，
batch 是 **10/12、106.99 秒**，context 是 **10/12、95.08 秒**。
不能只看时间就宣称当前方案已全面超过朴素组。

### 哪些收益可以解释，哪些还不能

- 并行准备对应的准备阶段累计时间从 52.29 秒降至 33.05 秒，与端到端减少
  19.49 秒方向和规模一致。但两组生成轨迹及成功率仍有差异。
- 标签缓存命中 63 次，tokenize 请求从 923 降至 519。观察到的总体收益为 5.2%；
  双方共同成功的 9 个任务中为 3.0%。
- 续接缓存命中 65 次，tokenize 请求进一步从 519 降至 199，准备阶段省 2.69 秒，
  但模型请求从 69 增至 72，完整任务反而多用 1.15 秒。减少 HTTP 不保证完整任务更快。
- 只开码表组仅命中 **1 次**。别名任务两轮直接走普通 edit，没有进入 compact_edit。
  这轮没有验证出码表的完整 Agent 净收益，不能把微基准结果直接外推。
- 本地路由实际触发 4 次，码表命中从 1 增至 2 次，推理请求从 73 降至 66；
  双方共同成功的 10 个任务中省 10.92 秒（9.8%）。这是路由在码表开启时的条件收益。
- 目录纠正只触发 2 次。总体耗时差不能全部视作这两次重定向的精确成本。
- 批量计划生成 30 份计划，推理请求从 71 降至 44；双方共同成功的 9 个任务中
  省 19.98 秒（22.2%）。这支持减少外层往返的方向，但仍是小样本观察。
- 上下文组只看双方共同成功的 10 个任务，82.52 → 79.46 秒，省 **3.06 秒（3.7%）**。
  全部样本的 11.1% 降幅有较大部分来自失败 CSV 更快结束，不能称为等质量加速 11.1%。

### 编辑内部与理想分类

- 紧凑生成：21 次均成功，26.56 → 24.62 秒，省 **1.94 秒（7.3%）**。
  这是普通工具编辑与完整紧凑路径的实现比较，包含提示、表示和准备差异。
- 动态码表：相同 21 次任务、15 次命中，24.62 → 17.64 秒，省 **6.98 秒（28.3%）**。
  在匹配命中的 15 次子集中，平均紧凑生成 1.169 秒、分类复用 0.703 秒。
- 精确回放：9/9 暖轮命中，零模型调用，单次约 **29 毫秒**，对应生成编辑约
  1.10～1.12 秒；这些只测内部编辑，且要求任务、路径、源码匹配。
- Schema 操作：浮点默认值暖轮 1.103 → 0.740 秒，help 暖轮 1.111 → 0.691 秒；
  不支持的别名仍生成参数。它不等于任意任务的分类式执行。
- 理想完整动作分类：三个规模均 3/3 对正确。服务阶段分别
  0.426 → 0.135、0.889 → 0.134、2.775 → 0.182 秒；HTTP 均值分别
  0.686 → 0.393、1.178 → 0.447、3.185 → 0.559 秒。
  离线候选准备不在这些时间内，服务阶段也不等于纯 GPU kernel 时间。

### 19 次失败的原因

18 次是 CSV：所有九种 TAIR 配置冷暖两轮都使用了 `text.splitlines()`，
它丢掉字段内部换行；朴素组两次都使用 `io.StringIO(text)` 并通过。
CSV 提示明确要求支持 quoted embedded newlines，属于真实未满足的要求。
该问题在关闭码表、批量、上下文约束时仍出现，不能单独归罪于某个新开关；
客户端的共同提示/工具选择/生成路径需要另行对照定位。

另一例是 base 的函数修复暖轮：功能修好但未新增要求的测试。
后验变异检查确认其他 19 份函数任务测试有效。
所有 120 份项目的公开 unittest 均通过，但外部 oracle 仍抓住上述 CSV 问题；
因此“模型说测试通过”不足以判定任务正确。原始失败产物没有修补或替换。

新增 harness/报告测试后仓库 **295 项测试通过**。源快照、逐请求记录、文件产物、
独立 unittest、分类旁路事件、用量与数学复核均在结果目录中，统一以 SHA256SUMS 冻结。
